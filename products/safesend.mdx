SafeSend combines Cardinal's pre-transaction risk evaluation with a delayed ERC-20 settlement path. When you create a SafeSend transfer, tokens are locked in the contract until a future release time you set — and you keep the ability to cancel and recover them before that window closes. Every transfer goes through the Protection API before any token approval or contract interaction, so you know the risk verdict before value moves.

<Warning>
  SafeSend is currently a testnet MVP operating on Arbitrum Sepolia with test USDC only. The contracts have not been externally audited and are not ready for unrestricted mainnet use. Do not use real assets.
</Warning>

## Why SafeSend exists

A standard on-chain token transfer is irreversible the moment it confirms. SafeSend introduces two protection points before value settles:

1. **Pre-signature risk evaluation** — the Protection API assesses the complete transaction intent and returns an ALLOW, REVIEW, or BLOCK decision before you approve or execute anything.
2. **On-chain cancellation window** — tokens are held in the SafeSend contract until the release time you specified, giving you a window to cancel and recover funds if something looks wrong.

## Transfer lifecycle

A SafeSend transfer moves through four distinct on-chain states. Once a transfer reaches `Cancelled` or `Released`, it cannot be processed again.

| Status | Value | Meaning |
|---|---:|---|
| `None` | 0 | No transfer exists for this ID |
| `Pending` | 1 | Tokens are locked; release time has not yet been reached |
| `Cancelled` | 2 | Sender cancelled; full locked amount was refunded |
| `Released` | 3 | Transfer settled; recipient received funds minus the platform fee |

```text
Pending → Cancelled  (sender cancels before releaseTime)
Pending → Released   (anyone triggers release at or after releaseTime)
```

## Protected flow

<Steps>
  <Step title="Compose the transfer">
    Enter the recipient address, token, amount, and the release time you want. Confirm you are on the correct network.
  </Step>
  <Step title="Run the Protection API check">
    Before any wallet prompt, call `POST /api/check-transaction` with the full transfer intent.
  </Step>
  <Step title="Evaluate the verdict">
    Read the `recommended_action` in the response. For `REVIEW`, display all findings and require explicit acknowledgment. For `BLOCK`, stop immediately — do not continue.
  </Step>
  <Step title="Preview the fee">
    Call `previewFee(amount)` to show the exact fee the user will pay. Display the recipient, amount, release time, fee, and contract destination clearly before any wallet interaction.
  </Step>
  <Step title="Approve the token transfer">
    Read the current allowance first. Only request an approval if needed, and approve the exact amount — never request unlimited approval by default. Wait for the approval transaction to confirm.
  </Step>
  <Step title="Create the SafeSend transfer">
    Call `createSafeSend(recipient, token, amount, releaseTime)`. Record the returned `transferId` and transaction hash.
  </Step>
  <Step title="Cancel or release">
    During the pending window, you can cancel and recover funds. Once the release time passes, anyone can call `releaseSafeSend` to settle the transfer.
  </Step>
</Steps>

## Contract functions

### Create a transfer

```solidity
createSafeSend(
  address recipient,
  address token,
  uint256 amount,
  uint256 releaseTime
) returns (uint256 transferId)
```

The contract requires a non-zero recipient address, a non-zero ERC-20 token address, an amount greater than zero, a release time in the future (later than the current block timestamp), and sufficient token allowance and balance. The full `amount` is transferred from the sender into the SafeSend contract, which records all transfer details at creation time.

### Cancel a transfer

```solidity
cancelSafeSend(uint256 transferId)
```

Cancellation is only available to the original sender, only while the transfer is `Pending`, and only before the `releaseTime`. On success, the status becomes `Cancelled` and the full locked amount returns to your wallet.

<Warning>
  You cannot cancel after the release time has passed. Always show the on-chain `releaseTime` as the authoritative deadline — do not rely solely on a local countdown timer.
</Warning>

### Release a transfer

```solidity
releaseSafeSend(uint256 transferId)
```

Release succeeds only when the transfer is `Pending` and the `releaseTime` has been reached. **Anyone** may call this function after that point — the recipient, the sender, or an automation service. The caller has no control over the destination or amount; the contract sends the net amount to the recorded recipient and the fee to the configured fee recipient.

```text
recipient amount = locked amount - stored fee amount
```

### Read transfer details

```solidity
getSafeSend(uint256 transferId)
```

Always read transfer state from the contract — treat it as the source of truth rather than any local or cached value.

| Field | Type | Description |
|---|---|---|
| `sender` | address | Wallet that created and funded the transfer |
| `recipient` | address | Wallet that receives funds after release |
| `token` | address | ERC-20 token locked in the contract |
| `amount` | uint256 | Total token amount locked |
| `feeAmount` | uint256 | Fee recorded at creation time |
| `releaseTime` | uint256 | Unix timestamp when release becomes available |
| `status` | enum | `None`, `Pending`, `Cancelled`, or `Released` |

### Preview the fee

```solidity
previewFee(uint256 amount) returns (uint256)
```

The fee is calculated in basis points:

```text
fee amount = amount × fee_bps ÷ 10,000
```

The current pilot rate is **2.5%** (250 bps). Always call `previewFee` to show users the exact deduction before they confirm; do not hardcode the rate in your application.

## Protection decisions in SafeSend

SafeSend uses the `recommended_action` returned by `POST /api/check-transaction` to gate the entire flow.

| Decision | SafeSend behaviour |
|---|---|
| `ALLOW` | Continue to fee preview, token approval, and transfer creation |
| `REVIEW` | Display all findings; require explicit user acknowledgment before continuing |
| `BLOCK` | Stop immediately — do not proceed to approval or contract execution |

<Warning>
  If the Protection API is unavailable or returns an error, treat the result as `BLOCK`. Never silently fall back to a default `ALLOW` or substitute mock data. Re-run the check if the recipient, token, amount, network, or release time changes.
</Warning>

## Contract events

| Event | When emitted |
|---|---|
| `SafeSendCreated` | A new transfer is funded and stored as `Pending` |
| `SafeSendCancelled` | The sender cancels before the release time |
| `SafeSendReleased` | Settlement completes after the release time |
| `FeeConfigUpdated` | An authorised fee manager updates the fee configuration |

You can index the first three events to keep transfer histories synchronised, but always confirm current state with `getSafeSend` before displaying actions.

## Application safeguards

- Always run the Protection API check before token approval or contract execution.
- Bind every verdict to the exact transaction intent that was evaluated.
- Never continue from `BLOCK`.
- Require explicit acknowledgment for `REVIEW`.
- Verify the wallet is on the correct network before every approval and contract call.
- Display amounts with correct token decimals; avoid floating-point arithmetic.
- Show the on-chain release time, not only a local countdown.
- Wait for confirmed transactions before updating displayed status.
- Prevent duplicate wallet submissions while a request is pending.
- Keep your Protection API credentials on a trusted backend, never in frontend code.
