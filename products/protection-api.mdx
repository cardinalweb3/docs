The Cardinal Protection API sits between a user's intent and their wallet signature. Before any token approval, contract call, or transfer is submitted on-chain, you send the transaction's key fields to the API and receive a machine-readable risk decision — ALLOW, REVIEW, or BLOCK — backed by a risk score and structured findings you can surface directly to the user.

<Note>
  The current backend is a professional MVP for sandbox integrations and controlled pilots. Production threat feeds, full RPC simulation, external contract-verification providers, partner-specific policies, and distributed rate limiting are planned upgrades. Use the API host and key supplied during onboarding.
</Note>

## Authentication

Your Cardinal onboarding contact provides the correct API base URL and an environment-specific API key. Send the key in the `x-api-key` request header on every call.

```http
x-api-key: your_api_key
```

<Warning>
  Keep your API key on a trusted backend. Never expose it in browser code, mobile bundles, browser storage, public repositories, analytics tools, or application logs. Keys can be scoped, rate-limited, revoked, or expired.
</Warning>

## Check a transaction

```http
POST /api/check-transaction
```

Call this endpoint before requesting any wallet signature, token approval, or contract execution. If the recipient, chain, token, amount, contract, approval amount, or permissions change, re-run the check against the updated intent.

### Request fields

<ParamField body="from_address" type="string" required>
  The sender's wallet address.
</ParamField>

<ParamField body="to_address" type="string" required>
  The recipient's wallet address.
</ParamField>

<ParamField body="chain" type="string" required>
  Chain slug for the target network. Supported values: `ethereum`, `bnb`, `polygon`, `base`, `arbitrum`, `optimism`, `solana`.
</ParamField>

<ParamField body="token" type="string" required>
  Token symbol for the asset being transferred, such as `USDC`, `USDT`, or `ETH`.
</ParamField>

<ParamField body="amount" type="number" required>
  The proposed transfer amount.
</ParamField>

<ParamField body="transaction_type" type="string">
  Describes the nature of the transaction. One of: `safe_send`, `approval`, `contract_interaction`, `swap`, `mint`.
</ParamField>

<ParamField body="contract_address" type="string">
  The contract address involved in the transaction, if applicable.
</ParamField>

<ParamField body="contract_verified" type="boolean">
  Whether the caller considers this contract verified or trusted on-chain.
</ParamField>

<ParamField body="approval_amount" type="string">
  The token approval amount for `approval`-type transactions. Pass `"unlimited"`, `"max"`, or an exact numeric amount as a string.
</ParamField>

<ParamField body="permissions" type="array">
  An array of strings representing requested contract functions or permissions (e.g. `["transferOwnership"]`).
</ParamField>

### Example request

```bash
curl -X POST https://api.cardinalweb3.com/api/check-transaction \
  -H "Content-Type: application/json" \
  -H "x-api-key: your_api_key" \
  -d '{
  "from_address": "0xAbCd...1234",
  "to_address": "0x9876...FeDc",
  "chain": "ethereum",
  "token": "USDC",
  "amount": 10000
}'
```

### Response fields

<ResponseField name="request_id" type="string">
  A unique identifier for this check. Store it for your audit trail and include it when contacting support.
</ResponseField>

<ResponseField name="risk_score" type="number">
  A summary risk score from 0 to 100. Use this as a summary signal, not the sole basis for a decision.
</ResponseField>

<ResponseField name="risk_level" type="string">
  A human-readable risk band derived from `risk_score`:

  | Level | Score range |
  |---|---|
  | `LOW` | 0 – 29 |
  | `MEDIUM` | 30 – 59 |
  | `HIGH` | 60 – 84 |
  | `CRITICAL` | 85 – 100 |
</ResponseField>

<ResponseField name="network_valid" type="boolean">
  Whether the network, address, and token combination is valid.
</ResponseField>

<ResponseField name="warnings" type="array">
  Plain-language warning strings suitable for display to end users.
</ResponseField>

<ResponseField name="findings" type="array">
  Structured findings that explain the risk decision. Each finding contains:

  <Expandable title="Finding object fields">
    <ResponseField name="code" type="string">
      A stable identifier you can use for frontend logic and localisation (e.g. `scam_address_high`).
    </ResponseField>
    <ResponseField name="source" type="string">
      The analysis layer that produced the finding: `network`, `scam`, `simulation`, or `risk`.
    </ResponseField>
    <ResponseField name="severity" type="string">
      Finding severity: `LOW`, `MEDIUM`, `HIGH`, or `CRITICAL`.
    </ResponseField>
    <ResponseField name="message" type="string">
      A plain-language description of the finding, suitable for display to the user.
    </ResponseField>
    <ResponseField name="recommended_action" type="string">
      The action recommended by this individual finding: `ALLOW`, `REVIEW`, or `BLOCK`.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="recommended_action" type="string">
  The overall decision for this transaction: `ALLOW`, `REVIEW`, or `BLOCK`. This is the primary field your integration should act on.
</ResponseField>

<ResponseField name="checked_at" type="string">
  ISO 8601 timestamp of when the check was performed.
</ResponseField>

### Example response

```json
{
  "request_id": "req_7f3a9b2c",
  "risk_score": 72,
  "risk_level": "HIGH",
  "network_valid": true,
  "warnings": [],
  "findings": [
    {
      "code": "scam_address_high",
      "source": "scam",
      "severity": "HIGH",
      "message": "Recipient address flagged in threat feed",
      "recommended_action": "BLOCK"
    }
  ],
  "recommended_action": "BLOCK",
  "checked_at": "2026-08-02T10:15:33.000Z"
}
```

## Decision handling

Every response carries a `recommended_action` field. Your integration must honour it — do not make decisions based on `risk_score` alone.

| Decision | Meaning | Required action |
|---|---|---|
| `ALLOW` | Low risk, no significant findings | Proceed with the transaction |
| `REVIEW` | Elevated risk, findings warrant attention | Show warnings and findings; require explicit user acknowledgment before continuing |
| `BLOCK` | High or critical risk | Stop the transaction immediately; do not proceed |

<Warning>
  Never override a `BLOCK` decision without an explicit, user-initiated acknowledgment flow. If your integration encounters an error, a timeout, or any non-success response, treat it as `BLOCK`. Do not silently fall back to a default `ALLOW` or substitute mock data.
</Warning>

## Rate limit headers

Every protected transaction check response includes rate limit headers so you can track usage and handle limits gracefully.

```http
X-RateLimit-Limit: 300
X-RateLimit-Remaining: 299
X-RateLimit-Reset: 2026-08-02T10:01:00.000Z
```

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Maximum number of requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests remaining before the limit is reached |
| `X-RateLimit-Reset` | ISO 8601 timestamp when the rate limit window resets |

Limits vary by pilot key. If you exceed the limit, the API returns `HTTP 429 Too Many Requests`.

## Error responses

| Status | Cause | How to handle |
|---|---|---|
| `401 Unauthorized` | Missing or invalid API key | Check your `x-api-key` header |
| `429 Too Many Requests` | Rate limit exceeded | Back off and retry after `X-RateLimit-Reset` |
| `4xx` / `5xx` | Validation failure or service error | Treat as `BLOCK`; log the `request_id` if available |

## Integration sequence

<Steps>
  <Step title="Compose the transaction intent">
    Gather `from_address`, `to_address`, `chain`, `token`, `amount`, and any optional fields relevant to the transaction type.
  </Step>
  <Step title="Call POST /api/check-transaction">
    Send the intent to the Protection API before any wallet prompt, token approval, or contract call.
  </Step>
  <Step title="Evaluate the recommended_action">
    Read `recommended_action` from the response. Surface `findings` and `warnings` to the user when the decision is `REVIEW` or `BLOCK`.
  </Step>
  <Step title="Enforce the decision">
    Continue only for `ALLOW`, or for `REVIEW` after the user explicitly acknowledges the findings. For `BLOCK`, stop the flow immediately.
  </Step>
  <Step title="Request the wallet signature">
    Only after a clear `ALLOW` or acknowledged `REVIEW` should you request token approval, signature, or contract execution.
  </Step>
</Steps>
