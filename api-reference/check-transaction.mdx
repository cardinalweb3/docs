title: "POST /api/check-transaction — Transaction Risk Check"
sidebarTitle: "check-transaction"
description: "Evaluate a transaction's risk before requesting a wallet signature. Returns a risk score, findings, and a recommended action of ALLOW, REVIEW, or BLOCK."
---

The `/api/check-transaction` endpoint is the core of Cardinal's protection layer. You call it with a complete description of the transaction you intend to execute — sender, recipient, chain, token, and amount — and Cardinal returns a machine-readable risk verdict before any value moves. Build your integration logic around the `recommended_action` field: proceed on `ALLOW`, gate on `REVIEW`, and stop on `BLOCK`.

## Endpoint

```http
POST https://api.cardinalweb3.com/api/check-transaction
```

## Authentication

All requests to this endpoint require an API key passed in the `x-api-key` header. Cardinal issues keys per partner and environment during onboarding. Keys are stored as hashes and can be scoped, rate-limited, revoked, or expired.

```http
x-api-key: your_api_key
```

<Warning>
  Keep your API key on a trusted backend server. Never expose it in browser code, mobile bundles, browser storage, public repositories, analytics pipelines, or logs.
</Warning>

## Request body

### Required fields

<ParamField body="from_address" type="string" required>
  Sender wallet address. For EVM chains, this must be a valid `0x`-prefixed 40-character hex address. For Solana, provide a valid base58 address.
</ParamField>

<ParamField body="to_address" type="string" required>
  Recipient wallet address. Follows the same format requirements as `from_address` — EVM chains expect a `0x`-prefixed 40-character hex address, and Solana expects a valid base58 address.
</ParamField>

<ParamField body="chain" type="string" required>
  Blockchain identifier for the transaction. Must be one of the supported chain slugs listed below.

  | Network   | Value        |
  | --------- | ------------ |
  | Ethereum  | `ethereum`   |
  | BNB Chain | `bnb`        |
  | Polygon   | `polygon`    |
  | Base      | `base`       |
  | Arbitrum  | `arbitrum`   |
  | Optimism  | `optimism`   |
  | Solana    | `solana`     |
</ParamField>

<ParamField body="token" type="string" required>
  Token symbol for the asset being transferred or approved. Examples: `USDC`, `USDT`, `ETH`, `SOL`, `BNB`.
</ParamField>

<ParamField body="amount" type="number" required>
  Token amount involved in the transaction. Must be a positive number.
</ParamField>

### Optional fields

<ParamField body="transaction_type" type="string">
  Classifies the type of transaction being checked. Accepted values: `safe_send`, `approval`, `contract_interaction`, `swap`, `mint`. If omitted, the check defaults to a standard transfer.
</ParamField>

<ParamField body="contract_address" type="string">
  Address of the smart contract being interacted with. Required when `transaction_type` is `contract_interaction`.
</ParamField>

<ParamField body="contract_verified" type="boolean">
  Whether the contract at `contract_address` is verified on-chain. Defaults to `false` when `contract_address` is present and this field is omitted.
</ParamField>

<ParamField body="approval_amount" type="number">
  Token amount being approved. Required when `transaction_type` is `approval`.
</ParamField>

<ParamField body="permissions" type="array">
  Array of permission strings or function selectors being requested by the transaction. Examples: `setApprovalForAll`, `transferOwnership`. Providing this field allows Cardinal to flag high-risk permission patterns.
</ParamField>

## Response

A successful check always returns the same stable shape. Your integration must act on `recommended_action` — do not derive the decision from `risk_score` alone.

<ResponseField name="request_id" type="string">
  Unique identifier for this risk check. Store this value in your audit trail and include it in any support requests related to the transaction.
</ResponseField>

<ResponseField name="risk_score" type="number">
  Numeric risk score from 0 to 100. Higher values indicate greater risk. Use this as a summary signal, not as the sole decision input.
</ResponseField>

<ResponseField name="risk_level" type="string">
  Qualitative label derived from `risk_score`.

  | Label      | Score range |
  | ---------- | ----------- |
  | `LOW`      | 0 – 29      |
  | `MEDIUM`   | 30 – 59     |
  | `HIGH`     | 60 – 84     |
  | `CRITICAL` | 85 – 100    |
</ResponseField>

<ResponseField name="network_valid" type="boolean">
  `true` when the network, addresses, and token combination passed Cardinal's validation checks. A `false` value indicates the request contains an unrecognised or invalid combination.
</ResponseField>

<ResponseField name="warnings" type="array">
  Array of plain-language warning strings intended for display to the end user. May be empty.
</ResponseField>

<ResponseField name="findings" type="array">
  Detailed findings from each risk evaluation layer. Each object in the array explains one specific reason contributing to the overall verdict.

  <Expandable title="Finding object fields">
    <ResponseField name="code" type="string">
      Stable machine-readable identifier for the finding type. Use this in your frontend logic to map findings to custom copy or UI treatment.
    </ResponseField>

    <ResponseField name="source" type="string">
      The risk layer that produced this finding. One of: `network`, `scam`, `simulation`, `risk`.
    </ResponseField>

    <ResponseField name="severity" type="string">
      Severity of this individual finding: `LOW`, `MEDIUM`, `HIGH`, or `CRITICAL`.
    </ResponseField>

    <ResponseField name="message" type="string">
      Plain-language description of the finding, suitable for display to the end user.
    </ResponseField>

    <ResponseField name="recommended_action" type="string">
      The action recommended by this specific finding: `ALLOW`, `REVIEW`, or `BLOCK`. The top-level `recommended_action` represents the aggregate verdict across all findings.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="recommended_action" type="string">
  The primary field your integration logic should act on. One of:

  | Value    | Required behaviour |
  | -------- | ------------------ |
  | `ALLOW`  | Continue to the wallet signature, token approval, or contract call |
  | `REVIEW` | Display all findings and require the user's explicit acknowledgement before continuing |
  | `BLOCK`  | Stop the transaction flow immediately; do not proceed |
</ResponseField>

<ResponseField name="checked_at" type="string">
  ISO 8601 timestamp of when the risk check was performed.
</ResponseField>

## Rate limit headers

Every response from this endpoint includes rate limit information:

```http
X-RateLimit-Limit: 300
X-RateLimit-Remaining: 299
X-RateLimit-Reset: 2026-08-02T10:01:00.000Z
```

`X-RateLimit-Limit` is the maximum number of requests allowed in the current window. `X-RateLimit-Remaining` is the number of requests remaining. `X-RateLimit-Reset` is the ISO 8601 timestamp when the window resets. Exceeding the limit returns `HTTP 429`.

## Error responses

### Missing or invalid API key

```http
HTTP 401 Unauthorized
```

The response body indicates `Missing API key` or `Invalid API key`. Verify that you are passing the correct key in the `x-api-key` header.

### Rate limit exceeded

```http
HTTP 429 Too Many Requests
```

```json
{
  "statusCode": 429,
  "message": "Rate limit exceeded"
}
```

### Validation or service failure

Treat any non-2xx response as a failed protection check. Display a real error to the user, retain the `request_id` when one is present in the response body, and never silently substitute a mock verdict or default `ALLOW`.

## Integration sequence

Cardinal's protection check must run before any value moves. Re-check if the recipient, chain, token, amount, contract address, approval amount, or permissions change after the initial check.

```text
Compose transaction intent
→ POST /api/check-transaction
→ Render ALLOW, REVIEW, or BLOCK with findings
→ Continue only for ALLOW or an explicitly acknowledged REVIEW
→ Stop for BLOCK
→ Only then request token approval, signature, or contract execution
```
