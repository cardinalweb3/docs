Every error response from the Cardinal API uses a consistent JSON shape with a `statusCode` integer and a human-readable `message` string. Handling errors correctly — especially by applying the fail-closed rule — is a security requirement, not just a reliability concern.

## Error response format

All API errors return a JSON body in the following structure:

```json
{
  "statusCode": 401,
  "message": "Invalid or missing API key"
}
```

Where available, the response also includes a `request_id` field that you can share with Cardinal support to trace a specific call.

## Error codes

| HTTP Status | Meaning | Recommended Action |
|-------------|---------|-------------------|
| `400` | Invalid request body — a required field is missing or has the wrong type | Review the request schema and verify all required fields are present and correctly typed |
| `401` | Missing or invalid API key | Confirm the `x-api-key` header is set and matches the key issued during onboarding |
| `422` | Validation error — a field value is not supported (for example, an unsupported chain) | Check the field value against the list of supported values in the API reference |
| `429` | Rate limit exceeded | Back off and retry; read the `X-RateLimit-Reset` header to determine when to resume |
| `500` | Internal server error | Treat as `BLOCK` — fail closed; retry with exponential backoff after a short delay |
| `503` | Service unavailable | Treat as `BLOCK` — fail closed; queue the request and retry when the service recovers |

## The fail-closed rule

<Warning>
  **Any non-2xx response from the Cardinal API must be treated as a `BLOCK` decision.** This is a security requirement. If Cardinal is unreachable, returns an error, or exhausts your retry budget, your application must stop the transaction flow — never silently allow a transaction to proceed when the risk check could not be completed. Failing open (defaulting to ALLOW on error) defeats the purpose of transaction protection and creates an exploitable gap in your security posture.
</Warning>

A practical implementation looks like this: if your Cardinal API call throws an exception or returns any status outside the `2xx` range, render the same blocked state you would for a `recommended_action: "BLOCK"` response, log the `request_id` if one was returned, and surface a clear error message to the user rather than a silent fallback.

## Error examples

**Validation error — unsupported chain:**

```json
{
  "statusCode": 422,
  "message": "Unsupported chain: tron"
}
```

Check the supported chains listed in the [Check Transaction](/api-reference/check-transaction) reference and update your request accordingly.

**Rate limit exceeded:**

```json
{
  "statusCode": 429,
  "message": "Rate limit exceeded"
}
```

See [Rate Limits](/api-reference/rate-limits) for a full backoff implementation and guidance on reading the `X-RateLimit-Reset` header.

## Debugging unexpected decisions

If a transaction receives a `REVIEW` or `BLOCK` decision that you did not expect, inspect the `findings` array in the successful `200` response body. Each finding explains exactly why the decision was made:

| Field | Type | Description |
|-------|------|-------------|
| `code` | string | Stable identifier you can use in frontend logic and alerting rules |
| `source` | string | The detection layer that produced this finding: `network`, `scam`, `simulation`, or `risk` |
| `severity` | string | `LOW`, `MEDIUM`, `HIGH`, or `CRITICAL` |
| `message` | string | Plain-language explanation suitable for display to your users |

For example, if a transaction is blocked due to an unlimited token approval, the findings array will contain:

```json
{
  "findings": [
    {
      "code": "unlimited_token_approval",
      "source": "simulation",
      "severity": "HIGH",
      "message": "Unlimited token approval detected",
      "recommended_action": "BLOCK"
    }
  ]
}
```

Use the `code` field for programmatic handling (for example, to display a specific UI state) and the `message` field for user-facing copy. If you need to escalate an unexpected decision to Cardinal support, always include the `request_id` from the response.
