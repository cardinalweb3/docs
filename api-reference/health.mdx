The `/health` endpoint lets you verify that the Cardinal Protection API is reachable and operational. It requires no authentication and returns a simple JSON status object. Use it for infrastructure liveness checks, uptime monitoring, and readiness verification before sending your first real transaction check in a new environment.

## Endpoint

```http
GET https://api.cardinalweb3.com/health
```

## Authentication

None. This endpoint is public and does not require an `x-api-key` header.

## Request

No request body or query parameters are needed.

```bash
curl https://api.cardinalweb3.com/health
```

## Response

```json
{
  "status": "ok",
  "service": "Cardinal Protection API"
}
```

| Field     | Type   | Description                                      |
| --------- | ------ | ------------------------------------------------ |
| `status`  | string | `"ok"` when the service is healthy and reachable |
| `service` | string | Human-readable service name                      |

## Use cases

**Liveness checks** — Integrate `/health` into your load balancer or container orchestration health probe to confirm the API process is running.

**Pre-flight readiness** — Poll `/health` before your application sends its first `POST /api/check-transaction` call in a new deployment or after a network event, so you can surface a clear error to users rather than a confusing failed risk check.

**Uptime monitoring** — Configure your monitoring tool (for example, Datadog, UptimeRobot, or Grafana) to alert when `/health` stops returning `200 OK`. This gives you early warning of any availability issue before it affects production transaction flows.

<Note>
  A `200 OK` from `/health` confirms basic API reachability. It does not guarantee that downstream risk intelligence services or rate-limiting infrastructure are fully operational. If `/health` is healthy but `POST /api/check-transaction` is returning errors, contact Cardinal support and include the `request_id` from any failed check responses.
</Note>
