Cardinal authenticates every API request using an API key that you pass in the `x-api-key` request header. There are no OAuth flows or session tokens — a single header value is all that is required to make an authenticated call.

## Obtaining an API key

API keys are provisioned during the Cardinal pilot program. Contact your Cardinal onboarding representative to receive an environment-specific key for sandbox or production use. Cardinal stores all keys as hashes and never returns the raw value after initial provisioning, so store it securely as soon as you receive it.

## Passing your key

Include the `x-api-key` header on every request:

```bash
curl -X POST https://api.cardinalweb3.com/api/check-transaction \
  -H "Content-Type: application/json" \
  -H "x-api-key: your_api_key" \
  -d '{ "from_address": "0x123", "to_address": "0x456", "chain": "arbitrum", "token": "USDC", "amount": 500 }'
```

The header name is case-sensitive in some environments. Use exactly `x-api-key` (all lowercase) to avoid unexpected `401` responses.

## Key properties

Each API key has the following characteristics:

| Property | Details |
|----------|---------|
| **Scope** | Keys are scoped to specific operations. The current pilot scope is `transaction:check`. |
| **Rate limiting** | Each key carries its own rate limit. See [Rate Limits](/api-reference/rate-limits) for details. |
| **Revocable** | Cardinal can revoke a key at any time. Build your integration to handle `401` responses gracefully. |
| **Environment-specific** | Sandbox keys work only against sandbox infrastructure; production keys target production. Do not mix them. |

## Keeping your key secure

Your API key grants access to Cardinal's risk evaluation engine on your behalf. Follow these rules without exception:

- **Use a server-side proxy.** Your backend calls Cardinal; the browser or mobile app never touches the API directly. Never embed the key in frontend JavaScript, mobile bundles, or any client-side code.
- **Store keys in a secret manager.** Use a dedicated secrets service such as AWS Secrets Manager, HashiCorp Vault, or your cloud provider's equivalent. Do not store keys in environment files that are committed to version control.
- **Never commit keys to version control.** This includes `.env` files, configuration files, and any file that could be pushed to a repository — private or public.
- **Never include keys in logs or analytics.** Request logging pipelines can inadvertently capture headers; ensure `x-api-key` values are scrubbed before logs are written or shipped.
- **Rotate compromised keys immediately.** If you suspect a key has been exposed, contact Cardinal to revoke it and issue a replacement before resuming calls.

<Warning>
  A demo key is available for local development and testing only. It must never be used in a production environment or exposed in any publicly accessible system. Contact your Cardinal onboarding representative for your environment-specific key.
</Warning>

## Authentication errors

A `401 Unauthorized` response means the API key is missing or invalid. The most common causes are a missing header, a typo in the header name, or using a sandbox key against the production endpoint. Verify that the header is named exactly `x-api-key` and that the value matches the key issued during onboarding.

```json
{
  "statusCode": 401,
  "message": "Invalid or missing API key"
}
```

See the [Errors](/api-reference/errors) page for a full list of API error codes and recommended handling.
