Receiving a Cardinal decision is only half the work. Your integration is responsible for enforcing that decision faithfully — blocking what Cardinal blocks, escalating what Cardinal flags for review, and ensuring the transaction that gets signed is exactly the transaction that was checked. This page explains how to build that enforcement correctly.

## The Fail-Closed Principle

The most dangerous failure mode in any risk-gating system is failing open: allowing a transaction to proceed when the safety check could not complete. Cardinal integrations must always **fail closed**.

<Warning>
Treat every API error, network timeout, and service unavailability as a `BLOCK`. Never substitute a default `ALLOW`, a cached result, or a mock decision when the Cardinal check fails to return a definitive result.
</Warning>

If your system cannot obtain a fresh Cardinal decision for a transaction, the correct response is to pause or queue that transaction — not to proceed without a check. Build this behaviour explicitly into every error handler, timeout path, and retry-exhaustion branch.

## The 7-Layer Security Model

Cardinal sits at one layer in a broader transaction-security architecture. Each layer must pass before the transaction proceeds; a failure at any layer stops the flow.

<Steps>
  <Step title="Authentication">
    Your application authenticates the user and verifies their identity and organisational authority before any transaction is initiated.
  </Step>
  <Step title="Intent construction">
    Your backend constructs the final canonical transaction intent — serialised deterministically and hashed for tamper detection.
  </Step>
  <Step title="Cardinal check">
    Your backend submits the canonical intent to the Cardinal Protection API and receives an `ALLOW`, `REVIEW`, or `BLOCK` decision with supporting findings.
  </Step>
  <Step title="Policy evaluation">
    Your policy engine combines the Cardinal result with your internal rules, approval requirements, and compliance controls.
  </Step>
  <Step title="User or approver sign-off">
    For `REVIEW` decisions, a human explicitly acknowledges the risk. For high-value transactions, a second approver may be required.
  </Step>
  <Step title="Signing">
    The wallet or authorised signer verifies and signs the unchanged canonical intent. The signed payload must match the checked intent exactly.
  </Step>
  <Step title="Record">
    Your systems record the Cardinal decision, intent hash, policy result, and on-chain transaction hash together in a durable audit record.
  </Step>
</Steps>

## Decision Enforcement Table

Each Cardinal decision maps to a specific set of required actions. Your integration must implement all of them — you may be stricter, but you must not be weaker.

| Decision | Required Action |
|---|---|
| `ALLOW` | Proceed normally through your remaining internal controls |
| `REVIEW` | Show a clear warning, require explicit user acknowledgment, log the acknowledgment, then proceed |
| `BLOCK` | Stop the transaction completely, show a clear explanation to the user, log the block |
| Error / timeout | Treat as `BLOCK` — fail closed; pause or queue the transaction |

<Note>
Your policy may apply stricter rules than Cardinal — for example, blocking a transaction that Cardinal rated `REVIEW`. It must never silently weaken a `BLOCK` result.
</Note>

### TypeScript Decision Handler

The following example shows a complete decision handler that enforces all four outcomes, including the fail-closed error path.

```typescript
type CardinalDecision = 'ALLOW' | 'REVIEW' | 'BLOCK';

async function applyDecision(decision: CardinalDecision, requestId: string): Promise<void> {
  switch (decision) {
    case 'ALLOW':
      await proceedWithTransaction();
      break;

    case 'REVIEW':
      const acknowledged = await promptUserAcknowledgment();
      if (!acknowledged) throw new Error('User did not acknowledge REVIEW decision');
      await logAcknowledgment(requestId);
      await proceedWithTransaction();
      break;

    case 'BLOCK':
      await logBlock(requestId);
      throw new Error('Transaction blocked by Cardinal risk assessment');
  }
}

// Wrap all Cardinal calls to enforce fail-closed behaviour
async function checkAndEnforce(intent: TransactionIntent): Promise<void> {
  let decision: CardinalDecision;

  try {
    const result = await callCardinalAPI(intent);
    decision = result.recommended_action;
  } catch (err) {
    // Any error — network, timeout, 5xx — is treated as BLOCK
    await logFailClosed(intent, err);
    throw new Error('Cardinal check failed — transaction blocked (fail-closed)');
  }

  await applyDecision(decision, result.request_id);
}
```

## Check-to-Sign Binding

A Cardinal decision is valid only for the exact intent that was checked. Your integration must prevent any divergence between what Cardinal evaluated and what the signer ultimately signs.

<Steps>
  <Step title="Generate the payload from the checked intent">
    Build the signing payload directly from the canonical intent object that was submitted to Cardinal. Never reconstruct the intent from user-supplied browser data without server-side validation.
  </Step>
  <Step title="Apply a freshness window">
    Set a short timeout between the Cardinal check and the signing prompt. If the window expires before the user signs, invalidate the approval and re-check. The appropriate window length depends on your transaction value and risk tolerance.
  </Step>
  <Step title="Reject unexpected changes">
    If any security-relevant field changes between the Cardinal check and the signing prompt — recipient, amount, chain, token, contract, or approval scope — abort the transaction immediately and require a fresh check.
  </Step>
  <Step title="Verify at signing">
    Before presenting the signing prompt, recompute the intent hash and compare it against the hash stored with the Cardinal decision. Only proceed if they match.
  </Step>
</Steps>

## How to Prevent Tampering

Storing a cryptographic hash of the canonical intent with each Cardinal decision gives you a tamper-evident link between the evaluation and the signed transaction.

<Steps>
  <Step title="Hash the canonical intent">
    Serialise the intent deterministically and compute a SHA-256 hash of the serialised bytes. Store this hash on your backend — not in the browser.
  </Step>
  <Step title="Store the hash with the Cardinal decision">
    Persist the intent hash alongside the Cardinal `request_id`, `recommended_action`, `risk_score`, and `checked_at` timestamp in your transaction record.
  </Step>
  <Step title="Verify before presenting the signing prompt">
    Before showing the user the signing confirmation screen, recompute the hash from the current intent state and compare it against the stored hash. If they differ, something has changed — abort and re-check.
  </Step>
  <Step title="Compare broadcast transaction to checked intent">
    After the transaction is broadcast, verify that the on-chain parameters match the checked intent. Alert and halt automated settlement on any mismatch.
  </Step>
</Steps>

<Tip>
Store the intent hash in a backend session or database record, not in a cookie or local storage variable. Client-side storage can be modified by malicious scripts.
</Tip>

## Never Cache Decisions

Cardinal decisions are valid for a single transaction attempt at a specific point in time. Market conditions, contract states, address reputations, and risk signals can all change between attempts.

<Warning>
Always call Cardinal fresh for each transaction attempt. Do not reuse a previous decision — even if the intent appears identical, even if only seconds have passed, and even under high load or retry conditions.
</Warning>

Caching decisions introduces a window during which the risk profile of a transaction could change without your integration detecting it. The cost of an extra API call is far lower than the cost of an undetected risk.
