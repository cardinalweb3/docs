This page records confirmed public updates to Cardinal products and documentation. Each entry carries a status label so you know exactly what is available, what is pilot or testnet only, and what is still in development. Read the labels carefully before enabling any capability for customer funds.

<Note>
  An item listed in the changelog is not automatically approved for production use. Confirm the exact environment, network, asset, contract address, audit status, value limits, and partner agreement before going live.
</Note>

## Status labels

| Label | Meaning |
|---|---|
| **Available** | Publicly accessible capability confirmed for its documented scope |
| **Pilot** | Controlled partner or limited-access capability |
| **Testnet** | Uses test networks and test assets only |
| **Documentation** | Public documentation update — not a product deployment |
| **In development** | Not released for general production use |

### Protection API documentation baseline

**Available · Pilot**

Documented the current pre-transaction decisioning interface and its minimum integration contract. The following behaviours are confirmed:

- One submitted request represents one transaction intent
- Required fields: sender, recipient, network, token, and amount
- Explainable `ALLOW`, `REVIEW`, and `BLOCK` outcomes with a `findings` array
- Your policy remains authoritative and may be stricter than Cardinal's
- Changed transaction details require a new check
- Errors, timeouts, and unavailable service must never be converted into `ALLOW`

### SafeSend controlled MVP

**Pilot · Testnet**

Documented the verified SafeSend flow as a controlled Arbitrum Sepolia testnet MVP. The following are confirmed in scope:

- Wallet-connected protected-transfer flow using MetaMask
- Delayed and cancellable transfer design with a protection window
- Test USDC funding, cancellation, claim, expiry, and reconciliation guidance

**Not included in this release:**
- Unrestricted mainnet funds
- General production availability
- A guarantee that every transfer remains cancellable in every state
- Production contract addresses or external audit confirmation

---

### Programmable Escrow implementation guide

**In development · Documentation**

Published the confirmed contract lifecycle while keeping production readiness separate. The documented lifecycle covers: buyer-funded ERC-20 Escrow, seller acceptance, buyer release, pre-acceptance refund, timed seller claim, dispute initiation, resolver settlement, fee behaviour, and a threshold-approval contract pattern.

**Not confirmed in this release:**
- General mainnet availability
- Published production deployment addresses
- External audit completion
- Licensed or regulated escrow status
- Final arbitrator operations

## Release-note policy

Future entries should contain:

- Release date
- Product or documentation area
- Availability label
- Exact environment and network
- Added, changed, fixed, or deprecated behaviour
- Migration or customer action required
- Known limitations
- Contract addresses when publicly approved
- Audit and remediation status when confirmed
- Links to relevant guides

## Versioning guidance

Cardinal may use different version identifiers for APIs, applications, smart contracts, and documentation.

- **API versions** describe the request and response contract.
- **Application versions** describe public interface releases.
- **Smart-contract releases** must identify network and deployed address.
- **Documentation updates** describe guidance and do not change product behaviour by themselves.

Do not infer compatibility between versions. Confirm the version and environment included in the applicable partner agreement.

## Breaking changes

A future change is considered breaking when an existing integration must change to continue operating safely. Examples include:

- Required request-field changes
- Authentication changes
- Decision or finding schema changes
- Network or token identifier changes
- Contract replacement
- State-transition changes
- Removed or renamed endpoints
- Changed signature, approval, or permission requirements

Breaking changes will include migration guidance and an effective date where appropriate.
